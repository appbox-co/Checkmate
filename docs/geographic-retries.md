# Geographic confirmation and recovery checks

A newly failing geographic region is retried immediately through Globalping. A successful retry cancels the provisional failure. If the retry also fails or is inconclusive, that region stays pending without opening an incident or sending an outage notification. A later conclusive failure can open an outage only when its acquisition starts at least 60 seconds after the first failing acquisition started. Waiting for a slow provider response within one attempt does not satisfy this requirement. This confirmation applies to both geographic HTTP and ping monitors. Globalping may choose a different city or probe within the continent.

For geographic ping monitors, any received reply establishes reachability. Partial loss is stored as `packetLoss` (`sent`, `received`, `lost`, and percentage `percent`) in raw geographic samples and the existing authenticated geographic-history API; it does not mean the router is unreachable. A completed valid measurement with zero replies is a provisional failure. Explicit target or resolver failures remain failures; incomplete statistics, provider errors and offline probes are inconclusive. HTTP status-code handling is unchanged. Ping packet count remains the existing Globalping default of three per probe.

All measurements remain in raw geographic history. The public location status shows an unconfirmed failure as awaiting a check; overall availability and outage history use confirmed incidents. Alerts continue to name the failed geographic location.

Confirmed failed regions and regions awaiting confirmation are checked on the existing 60-second job interval. Pending regions get one follow-up measurement per job; they do not repeat the immediate retry. Success cancels a pending failure without a down/recovery notification pair. A new failure after success starts a new confirmation period. A successful recovery check clears that region immediately through the normal evaluator; a separate local outage can still keep the monitor down. Provider errors or missing probe results neither open an outage nor clear an existing one.

Healthy regions retain the configured geographic interval (15 minutes in production). The worker wakes each minute but only requests healthy-region probes when the next full sweep is due. Recovery attempts do not move that full-sweep timestamp. Probe execution, queue load and the existing scheduler retry/jitter can add delay; recovery is not guaranteed within exactly 60 seconds. Extra Globalping measurements are used only for confirmation, recovery or an overdue sweep with no usable provider result.

Full-sweep time, pending regions and their first-failure timestamps are stored with the existing monitor geographic state and survive worker restarts. The optional `pendingFailures` field needs no backfill. An already confirmed outage remains confirmed through an upgrade until a real successful check arrives. Older observations are treated as full sweeps. Pausing, maintenance suppression, configuration validation and notification routing use their existing paths. No new environment variables or external services are required.

## Validation and rollout

Run the geographicOutages and schedulerReconcile MongoDB integration tests, plus checkPipeline, geoChecksService, globalPingService, statusService and statusPageLocations unit tests. The integration cases cover immediate transient recovery, a 45-second failure with no incident or alert pair, delayed confirmation and restart, early/slow observations that must not confirm, provider failures, partial-loss persistence, local checks arriving during a retry, failed-region recovery, healthy-region cadence and incident/notification counts. Unit tests cover one/two/three replies, zero replies, malformed statistics, HTTP results and unavailable providers.

Deploy the server build onto the current production image, retaining its frontend and unrelated source boundaries. Back up the database and compose environment first. Reconciliation updates existing geo job intervals; if a failed region still has an old 15-minute next-run time, bring only its active geo job forward to within a minute. Verify the running image, worker health, persisted geo job intervals, public API and unchanged monitor/channel configuration. Keep the previous image and environment for rollback; no destructive database migration is required.
